MemT-1.0 — local memory vs hyper memory, and how training and inference use them

Paper: MemT-1.0: Towards Memory-Native Evolution — MemTensor Team, Oct 2026, arXiv:2610.26825 · code · models. This note covers the two kinds of memory, how each one changes in training and at inference, the tensor shapes of the read path and the gates, and how MemT compares with text memory and with a KV cache.

📄 Paper Summary

The idea in one picture

frozen LLM  +  a memory branch in some layers
each layer:  output = normal attention (current step only)  +  memory attention (reads M)
after each step:  write the step's tokens into M, token by token (erase · write · decay)
M has a FIXED size → the past never has to sit in the prompt

Training: 34B tokens, only the memory weights train

  1. Continued pre-training (20B tokens, cross-entropy): long text cut into 2K segments; the model sees only the current segment, so earlier segments must come through memory.
  2. Post-training (14B tokens, distillation): the teacher is the same backbone with the full text history; the student is backbone + memory with no history text. Loss = KL to the teacher's top-64 tokens on the answer tokens.

Analogythe notebook page — what is writtenthe note-taking skill — how to write and look things up

The backbone (35B) is a third part, frozen all the time.

How does training update them?
FORWARD   (one sample: 64K pack = 32 steps × 2K, then a query)
  M_1 = 0
  step 1: read M_1 → write step-1 tokens with φ → M_2
  step 2: read M_2 → write                      → M_3   ...   → M_33
  query:  read M_33 → predict answer
          loss = KL(full-context teacher ‖ student)     ← only on answer tokens

BACKWARD
  loss → reads of M_33 → back through every write step (32 … 1) → into φ
  update φ only · backbone frozen · M is thrown away

History tokens get no direct loss, but the gradient tells φ which history should have been kept to answer the question (paper: "gradients from response predictions propagate through memory readout and earlier storage operations").

How does inference use the memory?
new user → M = 0
step 1:  read M (empty) → answer → write turn 1 into M      (forward pass only)
step 2:  read M         → answer → write turn 2 into M
...
step 50: M holds 49 turns — still 40 MiB
user done → reset M (or save the 40 MiB to continue later)

No gradients and no weight changes at inference. M changes only because the write rule is part of the forward pass, like an RNN hidden state.

Why can memory "update with experience" — during inference or only training?

Experience updates the local memory M at inference, not the weights. In the agent experiment, experience text goes through one forward pass with writing on → M is updated → later actions read M → M is reset at the end of the task.

  • ✅ Updates during inference, within one user / task.
  • ❌ No learning across tasks: M is reset, and φ never changes from experience.
  • Consolidating local memory into hyper memory is listed as future work (Sec. 8).

So the hyper memory is the important part — it learns how to manage memory?

Yes. φ is the learned memory manager: WK, WV decide what to store; erase β, write ω and forget λ decide how much to remove, add and fade; WQ decides what to ask; the output gate decides how much to trust the readout. The ablation backs this up: no post-training −10.7, but a different update formula only −0.3 to −0.5.

Limits: φ is fixed after training (the same manager for every user), its gates see only the current token (it cannot decide "this is already stored, skip it"), and memory size, backbone and teacher still cap the result.

Q&A — steps and shapes

What is the step t?

One interaction step: input Xt + response Yt. Mt = memory before step t (holds steps 1 … t−1); it stays fixed while step t is read and generated, then the step's tokens are written one by one (index i) to give Mt+1. In practice a step is usually a 2,048-token chunk: a 128K history = 64 write steps.

IndexMeaning
twhich step / turn
iwhich token inside step t, when writing
kwhich token is being generated, when reading
Is it for multi-step conversation, not one-step QA?

Yes. With a single question and no history, M = 0, so the readout q·M = 0 and the model is just the backbone. But "multi-step" also covers one long input, since the paper cuts long text into 2K steps. The memory benchmarks write the history first (2K per step), then ask short questions that read the final memory. General-ability tests fill memory with unrelated noise first, to check that bad memory doesn't hurt.

What are the tensor shapes of MemoryAttention(H̃ ; Mt)? (Nano, one layer)
H̃  input hidden                                  (L, 2048)
Q  = L2Norm(H̃ · W̃_Q)      16 heads × (2048→256)   (16, L, 256)
R  = Q · M / sqrt(256)     M: (16, 256, 256)       (16, L, 256)   ← cost does not depend on history length
RMSNorm(R) per head                                (16, L, 256)
G  = H̃ · W_g/d · W_g/u     2048→256→256 per head   (16, L, 256)
RMSNorm(R) ⊙ SoftCapSiLU(G)   2·tanh(SiLU(G)/2)    (16, L, 256)
concat heads                                       (L, 4096)
+ backbone gated attention output                  (L, 4096)
frozen o_proj 4096→2048                            (L, 2048)  → residual

4096 = 16 × 256 matches the backbone's query heads, so memory is added before the frozen o_proj. W̃Q is copied from the backbone's query projection at init. While decoding one token, L = 1.

How are the gates generated — what input, what network?

Every gate is a linear projection of the current token's pre-norm hidden state H̃ only (no MLP, no input from M).

Init matters. The forget projection starts at 0 and its bias gives each key channel a half-life drawn from 2,048–32,768 tokens (decay per token 2−1/τ), so some channels start with short memory and some with long memory. The output gate starts near 0, so memory starts "off" and the model begins as the plain backbone.

Unlike LSTM gates, which also see the previous hidden state, MemT's gates see only the current token. That keeps the write fast and parallel, but the gate cannot react to what is already stored.

Notebook vs what stays in your head. The biggest gap is exact long recall: LongMemEval-S full context 77.8, MemOS 83.2, MemT-Flash 37.2.

Parametric memory vs KV cache?

MemT is basically a KV cache folded into one matrix:

KV cache:  keep (k_1,v_1) … (k_N,v_N)        read = Σ softmax(q·k_i) v_i      grows with N
MemT:      M ≈ Σ k_iᵀ v_i (+ erase, decay)    read = q · M                     fixed size

Nano KV per token = 10 layers × 2 KV heads × 256 × 2 (K,V) × 2 bytes = 20 KB
128K × 20 KB ≈ 2.5 GiB   vs   40 MiB  → ~63× (paper ~66×)
256K × 20 KB ≈ 5.0 GiB   (paper Fig. 3: 5.061 GiB ✓)

"Full context" in the paper is the KV-cache method: text → (encode once) → KV cache → (compress) → M.

But a KV cache can also be fixed-size, by token selection?

Yes — KV eviction (StreamingLLM, H2O, SnapKV, counter-causal eviction). Same budget: 40 MiB ÷ 20 KB ≈ 2,048 tokens kept exactly (1.6% of a 128K history) vs MemT's blurred trace of everything.

Both must decide before the question arrives. Their earlier model Metis used token selection; MemT replaced it, but the paper shows no Metis vs MemT comparison on memory benchmarks, and on SWE-bench Metis has higher pass^3 in all four settings (App. E). Open idea: exact top-B tokens + a compressed M together.
