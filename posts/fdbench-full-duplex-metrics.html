FD-Bench — Full-Duplex Metrics, Read Off a Timeline

Paper: FD-Bench: A Full-Duplex Benchmarking Pipeline Designed for Full Duplex Spoken Dialogue Systems — Peng, Chao, Ng, Ma, Ni, Ma, Chng (Alibaba-NTU CorpLab · NTU Singapore · Alibaba), arXiv:2507.19040 · code.

✅ Conclusion

  • Every metric is a timestamp subtraction or an event count. Silero-VAD marks when the user starts and stops, and when the AI starts and stops. Everything else is arithmetic on those four kinds of marks.
  • Five rates — SRR, SIR, SRIR, EIR, NIR — count whether the AI did the right thing. Four timings — IRD, FSED, ERT, EIT — count how many milliseconds late or early it did it. WER only checks the voice said the words the model itself wrote.
  • The script is an ordinary multi-round dialogue. What makes it full-duplex is that the audio is streamed nonstop with fixed silence gaps, so user speech can land on top of AI speech. Easy / Medium / Hard are the same conversations with gaps of 6–10 s, 4–6 s, 2–4 s.
  • That alone breaks the models. Moshi's SRR goes 61.7 → 45.6 → 34.1 across Easy/Medium/Hard. Same questions, same text — only the silence changed.

📄 Paper Summary

FD-Bench is an automatic benchmarking pipeline for full-duplex spoken dialogue systems, where the user can interrupt while the model is still speaking. GPT-4o writes multi-round conversations with five interruption types, TTS engines (ChatTTS, F5-TTS, CosyVoice2) turn the user side into a 40-hour speech corpus with MUSAN noise and controlled silence gaps, and Whisper plus Silero-VAD recover transcripts and timestamps from the model's output. From those timestamps the paper defines nine objective metrics for interruption handling and latency, plus GPT-4o subjective scores and Llama-3 conditioned perplexity for reply quality. Applied to Moshi, Freeze-Omni and VITA-1.5 over 293 conversations and 1,196 interruptions, all three degrade badly under frequent interruptions and background noise.

🖊 My Key Notes

The setting, in one paragraph

The benchmark plays fake user speech into the model, records what the AI says, and then uses Silero-VAD to get timestamps: when did the user start/stop talking, when did the AI start/stop talking. Every metric below is just counting events or measuring gaps between these timestamps.

Two kinds of user speech:

  • normal inquiry — the user asks while the AI is quiet.
  • interrupt inquiry — the user cuts in while the AI is talking.

And noise gaps — the silence between inquiries, where the benchmark inserts noise (door slam, music). The AI should ignore it.

The five rate metrics — counting events

MetricQuestion it asksCount / CountGood
SRRate (SRR)AI answered a normal question? Success-Replies / normal inquirieshigh
SIRate (SIR)AI stopped talking when the user cut in? Success-Interrupts / interrupt inquirieshigh
SRIRate (SRIR)After stopping, AI actually answered the new thing? Success-Replies-to-Interrupts / SIshigh
EIRate (EIR)AI cut into the user before the user finished? Early-Interrupts / all user inquirieslow
NIRate (NIR)Noise fooled the AI into reacting? Noise-Interrupts / noise gapslow
SRIR is the odd one. Its denominator is SIs, not all interrupts. So it only looks at the cases where the AI already stopped correctly. Stopping is step 1, answering is step 2, and the paper keeps them apart on purpose.

The four timing metrics — measuring milliseconds

MetricMeasured from → toGood
IRD interrupt-response-delayuser starts cutting in → AI goes quietlow
FSED first-speech-emit-delayuser stops talking → AI's first soundlow
ERT early-reply-timeAI starts its answer this many ms before the user finishedsmall
EIT early-interrupt-timeAI cuts into the user this many ms before the user finishedsmall

ERT and EIT look the same. The difference is intent: ERT is a correct answer that just started a bit too soon (a few hundred ms, almost human). EIT is the AI barging in and stopping the user — about 2 seconds early in the results, clearly wrong. All four are reported as medians, not means, so one broken 60-second delay does not ruin the number.

WER

Take the AI's own text output. Take the AI's speech output, run Whisper on it. Compare. This does not check if the answer is right — it checks if the voice really said the words the model wrote.

AI text output:      "the museum closes at five"
Whisper on AI audio: "the museum close  at nine"

5 words, 2 wrong ("closes"→"close", "five"→"nine")   →   WER = 2/5 = 40%

t=24.0  U stops

Now read the metrics off it:

  1. t=2.8 vs t=3.0 → AI began 200 ms before the user finished, and the answer was correct.
    → 1 Success-Reply (SR), ERT = 200 ms.
  2. t=5.0 → t=5.2 → noise made the AI shut up.
    → 1 Noise-Interrupt (NI). Bad. This feeds NIRate.
  3. t=7.0 → t=8.2 → user cut in, AI stopped 1.2 s later.
    → 1 Success-Interrupt (SI), IRD = 8.2 − 7.0 = 1200 ms.
  4. t=8.5 → t=9.7 → after the user finished, AI took 1.2 s to make its first sound, and it talked about lunch (the new topic).
    → 1 Success-Reply-to-Interrupt (SRI), FSED = 9.7 − 8.5 = 1200 ms.
  5. t=12.0 → user cut in, AI ignored it and kept talking.
    → not an SI. This one lowers SIRate. It can never become an SRI.
  6. t=22.0 vs t=24.0 → AI barged in 2 s before the user finished.
    → 1 Early-Interrupt (EI), EIT = 24.0 − 22.0 = 2000 ms.

Turning counts into rates

Say the whole run gives these totals:

normal inquiries          = 20     success replies (SR)    = 12
interrupt inquiries       = 40     success interrupts (SI) = 32
SIs                       = 32     replies to them (SRI)   = 24
all user inquiries        = 60     early interrupts (EI)   = 15
noise gaps                = 25     noise interrupts (NI)   = 10

SRR  = 12 / 20 = 60.0 %   (up is good)
SIR  = 32 / 40 = 80.0 %   (up is good)
SRIR = 24 / 32 = 75.0 %   (up is good)
EIR  = 15 / 60 = 25.0 %   (down is good)
NIR  = 10 / 25 = 40.0 %   (down is good)

Reading this AI: it stops well when interrupted (80%), and usually answers the interrupt after stopping (75%). But it only answers 6 out of 10 normal questions (60%), it barges into the user 1 time in 4, and noise fools it 4 times in 10. These numbers are close to Moshi's real row in Table 4 — SRR 61.7, SRIR 79.4, SIR 83.1, EIR 27.9.

Isn't this just a many-round conversation?

Half right. The text script is an ordinary multi-round conversation: GPT-4o writes it, up to 5 rounds, user speaks first. Nothing special there. The full-duplex part is not in the script — it is in how the audio is played into the model.

Normal multi-turn benchmark (turn-taking):

send U1  ->  wait for AI to finish  ->  send U2  ->  wait  ->  send U3

The test harness waits. User audio and AI audio never overlap. The AI is told where each turn starts and ends.

FD-Bench (full-duplex):

one long audio stream, sent in small chunks, never stopping:

[U1 speech][silence gap][U2 speech][silence gap][U3 speech]...

The client sends chunks of 80 ms (Moshi), 107 ms (Freeze-Omni) or 200 ms (VITA-1.5) and never waits for the AI. The gap length is set by a clock, not by the AI. So if the AI is still talking when the next user speech arrives, the two voices overlap — that is an interruption, and the AI must notice it and shut up. Nobody tells the AI that a new turn started. It has to find that itself.

This is the whole trick of the paper. Easy / Medium / Hard use the same conversations. Only the silence between them changes: 6–10 s, 4–6 s, 2–4 s. Nothing else. And that alone drives Moshi's SRR from 61.7 → 45.6 → 34.1. The model cannot handle speech arriving while it is still speaking.

Three things a turn-taking benchmark cannot have

  1. A "gap" to put noise in. In turn-taking there is no gap — the harness controls it. FD-Bench puts MUSAN noise in the silence gaps and asks: does the AI think the door slam is a user? That is NIRate. The metric simply does not exist in turn-taking.
  2. The AI talking over the user. In turn-taking the AI physically cannot, because it only gets the mic after the user turn is closed. In FD-Bench the AI can start at any millisecond, so EIRate and EIT become possible.
  3. Endpointing is part of the test. Turn-taking benchmarks do the segmentation for the model. Here the model does it, either inside itself (Moshi) or with an external VAD (Freeze-Omni threshold 0.8, VITA-1.5 threshold 0.7). Most of the bad results in the paper come from this — a wrong VAD threshold, not a weak LLM.

Rounds vs interruptions

They are different counts in the paper: 293 conversations, each up to 5 rounds — a round starts with a normal user question. Inside those, 1,196 interruptions, up to 4 per conversation — extra user speech thrown in while the AI is answering. Those are exactly the two denominators: rounds feed SRRate, interruptions feed SIRate.

Two results that show why the split matters

  • SIR and SRIR pull apart by interrupt type (Fig. 3). When the user says "sorry, can you repeat?", SIR is highest — easy to detect, the AI stops — but SRIR is low, because the models are bad at actually repeating. When the user asks a calm follow-up question, SIR is worst (hard to detect) but SRIR is best (once detected, the LLM answers it easily). One number alone would hide this.
  • Freeze-Omni has the best FSED (~450–500 ms, very fast to start talking) but a terrible IRD (over 10 seconds) and SRR near 11%. So "fast" and "handles interruptions" are separate abilities. Its VAD threshold of 0.8 blocks noise well (NIR only ~6%) but also blocks real user interrupts.
