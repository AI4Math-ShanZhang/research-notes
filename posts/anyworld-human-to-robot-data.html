AnyWorld — how a human video becomes robot training data

Paper: AnyWorld: Factorized Egocentric World Models for Cross-Embodiment Generalization — Chen, Bai, Wei, Chen, Zheng, Wu, Yang, Chen, Li, Yue, Guo, Ge, Lin & Liu (NTU · A*STAR · XPENG Robotics · Zhejiang · CUHK) · arXiv:2608.29242 · project page · code. Note focused on the data pipeline — how human experience is turned into robot supervision.

📄 Paper Summary

AnyWorld is a video world model that splits an egocentric interaction into three independent conditions — action, camera, and embodiment — so that a single human clip can be re-rendered with a robot body, in a new scene, or from a new viewpoint. It is trained in two stages on unpaired data (200K EgoDex human clips, then a small human + robot mix) and never sees the same interaction performed by both a human and a robot. The generated robot rollouts are paired with calibrated robot actions and used as extra adaptation data for a VLA, raising RoboCasa GR1 pick-and-place from 49.8% to 54.6% and real IRON grasping from 20.0% to 55.0%.

🖊 The action condition is a drawing, not numbers

This was the part I had to look at the figures to believe. A_1:T is a second video — same length, same resolution, blank white frames with a small coloured hand skeleton drawn on them. EgoDex is recorded with a headset that already tracks 3D hand pose, so you project those joints into the image plane and draw them.

The paper's reason:

"This places the action in the image plane, specifying where motion should occur in the video rather than how a particular body should actuate. Compared with joint commands or robot-specific action vectors, such pixel-space control provides a more embodiment-agnostic interface."

A joint-angle vector for a human arm means nothing to an IRON humanoid — different joint count, different limits. "The hand should be at this pixel, in this pose, at frame 12" makes sense for any body. That is the whole trick.

Three conditions, three different injection points, from a WAN Fun-Control 14B backbone:

action    H_in = Concat[ Z_s , Z^a_1:T , Z^0_1:T ]          # channel concat with the noisy latent  (eq 1)
camera    H_0  = PatchEmbed(H_in) + Adapter( Z^c_1:T )      # Plücker rays, added to patch embed    (eq 2)
embodiment H_l+1 = DiTBlock_l( H_l ; E_tau )                # text tag via cross-attention          (eq 3)

The embodiment tag is a structured caption that separates scene / action / subject, so only the subject phrase changes: "a human" → "an IRON humanoid robot" → "a RoboCasa GR1 robot".

🖊 There is no action prediction at inference

I got this wrong on first read, so it is worth stating plainly. Section 3.5: "Given a source video, we extract its action and camera controls." The action is copied from a human clip you already have. Nothing predicts it, and the VLA is not in the loop.

🖊 Where the first frame comes from — reverse pseudo-pairs

To re-embody, you need an edited first frame Ĩ_0 showing the robot in the human's scene. There is no paired data to train that editor on. The supplementary (§2.1) has a neat trick.

Open-domain image editors are much better at drawing plausible human hands than at drawing a specific robot morphology. So run the easy direction: take ~800 egocentric robot frames per embodiment, use Nano-Banana to edit the robot arms into human arms while holding camera, background, and object state fixed. Now (robot image, generated human image) is an approximately aligned pair — and you train the inverse human→robot editor on it.

Cheap, and it sidesteps the impossible requirement of reproducing the same contact state with two different bodies.

🖊 Wrist path → gripper path, the seven steps

The main text says only "an action-calibration module maps the human wrist trajectory into the target robot's relative end-effector action space" and defers. The recipe is in supplementary §2.4, and it is a fixed geometry pipeline — no learning:

1. resample   16 FPS (EgoDex) → 30 FPS (IRON), cut to 50 steps   = 1.67 s, one action chunk
2. interpolate  position: linear in R^3      rotation: SLERP on SO(3)
3. relativize   donor-relative local deltas   ← this is where body size / arm length drops out
4. hand         project active side into the IRON-hand PCA action subspace   ("eigengrasps")
5. rescale      three separate factors: position, velocity, rotation
6. clip         to the valid IRON dynamic range
7. re-anchor    onto the robot's own S0, then RelativeActionTransform (same one used at deployment)

   non-target arm: held close to its initial state

Step 3 is the one that makes the transfer legal. Instead of "the wrist is at (0.31, 0.05, 1.42) in the room" you get "the wrist moved 4 cm forward and turned 3 degrees since last step." Where the person stood, how tall they were, how long their arm was — all gone. Only the shape of the motion survives.

Step 4 is the answer to "how does a five-finger hand become a gripper command": you do not solve it, you project onto the robot's own low-dimensional grasp basis and keep whatever lands there.

So the human motion is used twice, in two formats, from the same source trajectory:

human 3D wrist/hand trajectory
   ├─► project + draw ──► A_1:T  (picture)  ──► world model ──► V̂  robot video   [the observation]
   └─► calibration    ──► Ã_1:T  (numbers)  ─────────────────────────────────────► [the action label]

training item:   D_trans = { ( V̂_1:T , ℓ , Ã_1:T ) }     (eq 4)

The UniT baseline already pretrains on large-scale EgoDex, so the gain is not "human data helps" — it is "re-embodied human data helps on top of raw human data." That is the right control and I am glad they ran it.

🖊 What I take away

The contribution is the interface, not the model. The backbone is off-the-shelf WAN Fun-Control, and a control video is exactly what it already eats. What is new is deciding that action = a drawing, which is what makes human and robot share one conditioning channel and lets unpaired training work at all.
Things that bother me.
  • Nothing checks the video against the action. Ã comes from the original human trajectory; V̂ comes from a diffusion model. If the generated robot hand drifts off the skeleton, the label is silently wrong for that video. No filtering step is described anywhere.
  • The scale factors are never printed. "Calibrate position, velocity, and rotation scales" — with no values, and no description of how the IRON-hand PCA basis was fitted or how many components it keeps.
  • The mixing ratio does not agree with itself. Table 3 concludes "we therefore use the 2:1 mixture for our main model", the setup says 5K human + 5K robot, and supplementary §2.2 says "we maintain a 1:1 ratio between human and robot data within each epoch" with the human subset re-sampled each epoch. Possibly reconcilable, but as written the three statements do not line up.
  • n = 20. The headline 20% → 55% real-robot jump is 20 grasp trials of one object. That is 4 successes versus 11. Directionally fine, but it is a very thin plank for a +35 point number.
  • The calibration is only spelled out for IRON, under §2.4 "Targeted Human-to-IRON Visual–Action Pair Construction" — i.e. for the Section 4.6 closed-loop experiments. Whether the main-table pipeline is identical is not stated.
  • It needs tracked 3D hand pose. EgoDex ships it for free. Point this at ordinary internet video and both branches die at once — no skeleton to draw, no trajectory to calibrate.

In one paragraph: AnyWorld takes a human clip, keeps its hand-skeleton control video and its camera path, swaps only the first frame and the embodiment tag, and generates the same interaction performed by a robot in a different scene. In parallel a non-learned geometry pipeline turns the same human wrist trajectory into relative end-effector actions — resample, SLERP, go relative, project the hand onto a PCA grasp basis, rescale, clip, re-anchor on the robot's own start state. Video plus instruction plus calibrated action is a normal VLA training triple, and mixing those synthetic triples 1:1 with real robot data is what produces the reported gains. Never any paired human–robot clips, and never any check that the two halves of each generated triple actually agree.
