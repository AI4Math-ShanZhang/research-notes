BagelVLA — Enhancing Long-Horizon Manipulation via Interleaved Vision-Language-Action Generation

Paper: Yucheng Hu et al., February 2026, arXiv:2602.09849 · project page. Note from working through it — focused on Figure 3 (the three dual-denoising schemes) and how the language step is actually scheduled at run time.

📄 Paper Summary

The problem. Most VLAs learn a direct map from instruction to action. That breaks on long-horizon jobs, because one instruction — "stack the cubes red → yellow → blue → green" — silently contains a chain of separate stages. The policy has no place to record which stage it is in.

The move. Don't compress the chain. Write it out. BagelVLA factorizes the task into three generations that happen in order, in one token sequence:

p(a_t, v_t+k, l_t | v_t, L)  =  p(l_t   | v_t, L)              ← 1. subtask TEXT
                              · p(v_t+k | v_t, L, l_t)         ← 2. goal IMAGE
                              · p(a_t   | v_t, L, l_t, v_t+k)  ← 3. ACTION chunk

  L    = global instruction        l_t   = the immediate subtask
  v_t  = current observation       v_t+k = predicted keyframe

Each stage sees everything before it and nothing after. Language is trained with plain cross-entropy; the keyframe and the action are each trained with flow matching.

The architecture. A Mixture-of-Transformers: three experts sharing one attention stream, so it is one sequence, not three pipelined models. Understanding and generation experts are initialized from Bagel and follow Qwen2.5-7B; SigLIP2 encodes views for understanding, the FLUX VAE encodes images for generation. The action expert copies the Qwen2.5 shape but shrinks the MLP to 1/5, giving 2B — small on purpose, so it can be re-run fast.

Public datasets without subtask labels (Bridge, EgoDex, AgiBot) get them synthesized by Seed-1.5-VL-thinking, which also picks the temporal boundaries, then filtered.

Figure 3 — the three dual-denoising schemes

Two flow-matching processes run in the same sequence: the generation expert denoises the keyframe, the action expert denoises the action chunk. The keyframe is built up over ~50 steps. So the question is at which moment does the action expert read the image branch?

(a) Complete Denoise. Finish the image completely, then start the action, conditioned on the clean picture. Cost is N1 + N2 steps, run back to back. This is the textbook world model + inverse dynamics combination — and the paper's own framing is that it is theoretically sound but pays twice and inherits every visual error.
(b) Joint Denoise. Both denoise in lockstep. At image step 5 the action is also at step 5 and attends to the half-noisy image. Cost drops to N steps.
(c) Single-Step Denoise. Run the image denoiser for one step, keep only its KV-cache, throw the rest away. The action expert conditions on that and denoises alone. 
(a)  image: noise → 1 → 2 → … → 50 → CLEAN PICTURE
                                          ↓
     action:                    noise → 1 → … → 10 → actions

(c)  image: noise → 1 → (stop, keep KV-cache)
                            ↓
     action:      noise → 1 → … → 10 → actions

On top of (c) they change one thing — where the image noise starts. That is Residual Flow Guidance:

naive single-step :  starting noise centered at ZERO           → build the future from nothing
RFG               :  starting noise centered at CURRENT FRAME  → predict only the CHANGE

RFG is free — same 1.23 s, better score — and it reaches good keyframes in ~10 denoising steps instead of 50, because the model no longer has to redraw the static background.

Two clocks at inference

The 7B experts are too slow to run every chunk, so their KV-cache is computed and then reused while only proprioception and the 2B action expert update. The approximation is made safe during training by randomly replacing the current frame with an older one, teaching the model to act correctly on a stale view.

OUTER (slow)  fresh image → new subtask → new keyframe → rebuild KV-cache
INNER (fast)  frozen cache + fresh proprioception → action chunk    ×N

1.2 s per chunk on one RTX 5090 · chunk size 48 → ~40 Hz
reusing the frozen cache                       → ~72 Hz

🖊 My Key Notes

The ranking in Table 4 says something the paper doesn't quite say out loud. The more the action depends on the actual generated image, the worse it does. Complete Denoise uses the finished picture and loses. Joint Denoise uses noisy pictures and loses harder. Single-step uses no picture at all and wins by a wide margin.

Their explanation is domain shift: Calvin ABC→D changes scene colors, generated intermediate states go out of distribution, and the action expert is dragged down with them. That is convincing. But follow it through and the visual branch here is not really working as a world model the policy consumes. It is working as a training objective and a feature extractor. The action never sees the future frame.

Which reframes the contribution. "Predict the future and act toward it" is the story; "let a generative branch shape the representation, then read it before it renders anything" is the mechanism. Same family as WorldDiT's trick of backpropagating an RGB loss through shared weights and then deleting the RGB branch at run time — different route, same underlying bet.

If the action reads the KV-cache after one step, what is actually in there?

Not pixels. One step out of fifty removes almost nothing, so the latent is still noise. But those noisy image tokens have attended to the instruction, the current view, and the subtask. So the cache holds something like the intent — "gripper moves left, picks the red block" — in feature space, before any paint hits the canvas.

With RFG the story sharpens: the starting noise is centered on the current frame, so the cache does carry real image content — the current observation, never the predicted future one. The paper's own reason for RFG > naive is exactly this: one step on pure Gaussian noise gives the action expert too little to stand on.

Does the language expert plan all the subtasks upfront?

No — and this is the whole point of the word interleaved. It emits only the immediate subtask, conditioned on the current camera view. As the scene changes it emits a new one. If the robot drops the block, the next view shows an empty gripper and the model says "pick up the red block" again instead of marching on to step 3. A fixed upfront list cannot do that.

Reusing the same subtask across several action chunks is correct, not a bug: "pick up the red block" takes 2–3 seconds of motion and one chunk covers well under a second. Re-running a 7B forward pass to regenerate the identical sentence would be pure waste.

Why is freezing the KV-cache not free, unlike normal LLM caching?

In text generation the cache is exact — past tokens genuinely never change, so their K/V are identical on recompute. Here the first thing in the sequence is the camera image, and the robot is moving. Freezing means acting on an old picture. That is a deliberate accuracy-for-speed trade, which is why the stale-frame training augmentation exists and why fresh proprioception is fed every chunk. The split ends up being: stale but rich (image, subtask, keyframe) versus fresh but thin (joint positions).

What I'd want before trusting it

1. The re-planning schedule is never specified. The paper describes the async mechanism and quotes 40 Hz / 72 Hz, but never says what triggers the outer loop — fixed interval? keyframe reached? confidence drop? That number decides whether the robot notices a failed grasp in 0.5 s or 5 s, and every long-horizon claim leans on it.
2. The headline multi-task table doesn't test the headline mechanism. Table 2 is explicitly run without subtask planning. So the 75.5 average is evidence for the pretraining and the backbone, not for interleaved planning. The paper is upfront about this and attributes it to implicit planning learned in Stage 1 — fair, but it means the two headline numbers support two different claims.
3. Baseline coverage in Table 1 has holes. RDT has no Calvin number, VPP has no RoboTwin numbers. The missing Calvin entry for "w/o textual planning" is explained in the caption (Calvin is single-step, so there is nothing to decompose); the other two gaps are not.
4. A number that repeats. "w/o keyframe forecasting" scores 3.345 on Calvin in Table 1, and "Single-step Denoise (Eq. 2)" scores 3.345 in Table 4 — different settings (Table 4 is single-view, 10k steps). Could be coincidence, could be a transcription slip. Worth checking against the appendix tables before quoting either.

The one-line version

Write the causal chain out instead of compressing it — subtask text, then goal image, then actions, all in one attention stream — but read the image branch before it draws anything, so the policy gets the planning signal without inheriting the rendering errors.
