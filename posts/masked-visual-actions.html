Masked Visual Actions for Unified World Modeling

Paper: Alzayer, Huang, Chen, Luey, Zhang, Agrawala, Wetzstein, Fei-Fei, Du, Wu & Huang (Stanford · UMD · Harvard), July 2026, arXiv:2607.19343 · project page. Short note — the key points from working through it, in plain words.

📄 Paper Summary

The idea in one line. Don't tell the video model the action with numbers. Draw it. The action is the robot arm painted onto the video, in the right pixels, in every frame. Everything else is gray. That gray video with an arm in it is the command.

Then one small change gives you two models for free. Reveal the robot pixels and the model fills in the scene — a forward model. Reveal the object pixels and the same model fills in the robot — an inverse model. Same weights, same input format, only the mask changes.

What goes in

INPUT
  reference frame I0   — the scene as it is now, full color
  masked video M ⊙ V   — the revealed entity, drawn in place, every frame
                         everything else = uniform gray
  text prompt          — kept deliberately high-level, so the model
                         must rely on the mask, not the words

OUTPUT
  the whole video V — the model paints back what it cannot see

CONDITIONING = plain concatenation in latent space
  (fine, because the mask is already lined up with the output pixels)

Training. ~1,000 DROID demos (both external cameras) + 4,000 RoboCasa examples — about 15 hours. LoRA rank 256 only, 10k steps, 8×H200, 4 days. Failure trajectories are kept on purpose, so the model can show an attempt that goes wrong instead of always succeeding.

🖊 Key Notes

1. Two ways to make the mask, and they are complementary

SegmentationRendering
HowSAM on a real video, prompt "a robotic arm"recorded joint angles + camera calibration → render the URDF mesh
Goodno calibration, any robot, can mask any entityyou can draw an action that has not happened yet
Badyou can't hand-draw one at test time; the cut-out shape leaks what was behind the armneeds calibration, and can only draw the robot

Two rendering details that matter: the mesh is drawn translucent so the arm never hides itself, and the gripper fingers are painted bright red so open-vs-closed is easy to see.

The rendering path is the one that makes this usable as a simulator. To ask "what if the arm did this instead?", you need to be able to produce the condition — and a URDF render of any joint trajectory gives you exactly that.

2. Forward and inverse are the same model, different mask

Split the scene into two roles:

  • active — moves by its own agency (robot arm, human hand)
  • passive — moves only because something pushed it (the mug, the drawer)
FORWARD :  show the ACTIVE  pixels  →  model fills in the PASSIVE
           "the arm moves like this — what happens to the scene?"

INVERSE :  show the PASSIVE pixels  →  model fills in the ACTIVE
           "I want the mug to move like this — what must the arm do?"
Why this is allowed. A video model already learns the joint story of everything in the scene, p(e₁, e₂, …, eₙ). Hiding a subset just asks for a conditional of that same joint. Forward and inverse are not two models — they are two questions to one model. Same trick as BERT, moved from words to pixels.

The model itself never learns the words "active" and "passive". It only learns fill in the gray. The active/passive split is how the humans choose to use it, not a property of the network.

3. The zero-shot inverse result is the surprise

They trained only on masks showing the robot. Not one inverse example. Yet at test time you can flip it, condition on the object, and it works. The paper says plainly that they expected to need inverse finetuning and did not.

Their reading: the condition lives in the same space the model already thinks in, so inverse is not a new task — only a new query.

To actually run it on a robot: inverse model makes a video of the arm → a small learned inverse-dynamics model reads that video → joint commands. On CoffeeServeMug in RoboCasa:

Diffusion Policy   50%
ACT                80%
SmolVLA            85%
Ours (inverse)     90%     ← and the video model never saw this task

4. Why a dense mask beats a sparse signal

The real answer is where the learning work has to happen.

SignalWhat the model must still figure out by itself
raw joint angles (7 numbers)forward kinematics + what this robot looks like + contact + scene response
end-effector markerthe rest of the arm + contact + scene response
skeleton stick figurethe arm's real shape and thickness + contact + scene response
masked visual actiononly: how does the scene react to these moving pixels

With a sparse signal the model must learn a translator: sparse code → robot appearance → contact → result. It can only learn that translator from the robots in 15 hours of data. So it quietly memorizes "skeleton shaped like this ⇒ draw a Franka with the standard gripper".

The dense mask deletes the translator. Appearance is handed over, not predicted. What's left to learn is contact and reaction — which is exactly what a pretrained video model already knows from internet video. Less to learn, and the leftover part is already covered by the prior. That is why 15 hours and a LoRA are enough.

Read the first block carefully. In-domain, sparse conditioning is not worse at all. The gap only opens once you leave the training distribution. So the failure of sparse signals is not a fidelity failure — it is a generalization failure of the learned translator. Masked actions have no translator to fail.

6. What it is used for

UseHowResult
Policy evaluationroll a policy out inside the video model, score the imagined videor = 0.982 with real success rate across RoboCasa tasks
Planningsample 10 trajectories from Diffusion Policy, simulate each, let Gemini 3.1 Pro pick the best+7 to +26 points across six tasks; keeps improving with N
Action extractioninverse model → video of the arm → learned IDM → joint commands90% vs 50/80/85 for DP / ACT / SmolVLA

The planning setup is test-time scaling in disguise: policy + video model = generator, VLM = verifier. The VLM prompt is worth noting — it is told to punish three specific world-model lies: ghost contact (gripper near but not touching), post-disengagement coasting (object keeps moving after the arm pulls back), and frame-jump glitches (the goal state just teleports in). The JSON schema forces the model to commit to the causal mechanism before the success flag, so the verdict is anchored on process, not on the last frame.

7. Limitations

  • Correlation, not causation — their own stated limit. It has not learned physics, it has learned what usually follows what.
  • Imagination is optimistic. The correlation with reality is excellent, but the video model reports higher success than reality, in both sim and real. Good for ranking trajectories; risky as an absolute score.
  • Speed. It is a 14B video diffusion model. Fine for offline Best-of-N, not for a control loop.
  • Calibration. The "just segment anything" freedom is real in the training pipeline, but the rendering path — the one you need at test time — still wants camera calibration.
  • Capped by the base model. The method re-purposes the video prior rather than extending it.

8. Where it sits

How the action is givenForward?Inverse?Crosses embodiments?
Ctrl-Worldraw end-effector stateyesnono — collapses

Masked Visual Actionsmask over space — pixels on one canvasyesyes, zero-shotyes

That middle row is the sharp comparison. Other unified models also mask, but they mask channels, so the forward/inverse switch works while the embodiment gap stays. Masking spatially puts the active and the passive entity on the same canvas — so the one switch buys both.

In one line. Masked visual actions turn the action into a picture of the robot drawn on the video itself, so the model only has to learn contact and reaction instead of also learning what each robot looks like — and because it is just masked fill-in, flipping which pixels you reveal turns the same checkpoint from a forward model into an inverse model for free.
